**This issue's original body is framed somewhat inaccurately due to a lack of ability to test upstream Tailscale behavior.** See [this comment for more details](https://github.com/juanfont/headscale/issues/3316#issuecomment-4879253307). Headscale appears consistent with Tailscale's behavior, and this is a feature request to allow formally emitting routes for domain names outside of base_domain.

---

### Current Behavior

Setting Extra DNS Records in Headscale that don't correspond to entries under dns.base_domain do not propagate to clients. 

Additionally, attempting to then set a custom dns server in split dns for an affected domain in the extra dns entries will cause the split dns resolver to be overridden by the extra dns entries, passing the extra dns entries through to clients.

### Expected Behavior

I'm not entirely sure *which* case if either is supposed to be valid. I was originally going to file domain support outside of base_domain sub entries as a feature request, but seeing the second part of this issue makes me question if it is supposed to work.

The desired behavior is in some way be able to set extra DNS entries for any domain on A, AAAA records. If it isn't intended to be possible, then split DNS entries shouldn't be able to cause normally filtered extra DNS entries to override the split DNS targets. 

If this is intentional, the current requirement to set supplementary split dns entries for extra dns records that should work isn't documented, nor to what extent one should write in split dns entries. Optimally, one shouldn't need to define split DNS entries for extra DNS records outside of dns.base_domain.

### Steps To Reproduce

Case A:
1. Create Headscale deployment with extra DNS records, at least one under the set dns.base_domain and one not under.
2. Register and connect a node, and test where each record points, if propagated to the node.
3. Note the record(s) under dns.base_domain register, but others don't.

Case B:
1. Use existing configurations from Case A.
2. Create Split DNS entry with a functional DNS server for each previously failed extra DNS record.
3. (Re)start Headscale deployment.
4. Connect the node again and test where each record points.
5. Note that each record now points based on extra DNS entries rather using the configured DNS server(s) in split DNS config

Created: 2026-07-03T20:45:51Z; updated: 2026-07-03T20:45:51Z

Both behaviours here are the documented tailscaled MagicDNS semantics rather than a headscale bug — here's the mechanism.

**Why a record outside `base_domain` doesn't resolve (case 1).** headscale only marks a name as "route this to MagicDNS" for `base_domain` + search domains and for explicitly configured split-DNS nameservers — `ExtraRecords` are passed through verbatim with no matching suffix generated (`hscontrol/types/config.go`: `cfg.ExtraRecords = dns.ExtraRecords`, `cfg.Routes = splitResolvers()`, `cfg.Domains = [BaseDomain]+SearchDomains`). On the client, a static record only resolves if the query is actually routed to the internal resolver, and Tailscale documents exactly this on the `Hosts` field:

> Adding an entry to Hosts merely creates the record. If you want it to resolve, you also need to add appropriate routes to Routes. — `tailscale.com/net/dns/config.go`

With native split-DNS (systemd-resolved / Windows NRPT) the OS only forwards suffixes in `MatchDomains` (= the keys of `Routes`, `net/dns/config.go` `matchDomains()`) to `100.100.100.100`; a name outside every route/suffix goes to the system resolver and the extra record is never consulted.

**Why adding a split-DNS entry makes the static record "win" (case 2).** That split entry creates a `Routes` suffix, so the client now routes the name to the internal resolver — and there `resolveLocal` checks the host table *before* forwarding (`net/dns/resolver/tsdns.go`: `hosts[domain]` is matched at the top, forwarding only happens on the `RCodeRefused` fall-through). So the static record answers instead of your `1.1.1.1` resolver.

One caveat that explains the "odd/inconsistent" feel: on Apple platforms (and whenever Tailscale is set as a *global* resolver) everything is intercepted, so an extra record resolves even without a matching route (`net/dns/manager.go`, the non-split-DNS branch). So the "outside base_domain" case is platform-dependent.

Net: resolving arbitrary names outside `base_domain` would require headscale to emit a matching route/suffix for them, which is a feature rather than a fix.
