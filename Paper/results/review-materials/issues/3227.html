OK, I have more info about reproducing the bug, having talked in Discord:
The error messages are poor, that's the real problem here.
Here's no problem binding to port 80, when config.yaml has these changes:

server_url: https://myrealdomain.com/
listen_addr: 0.0.0.0:80
tls_letsencrypt_hostname: ""

Here's where no possible binding to port 80 occurs:

server_url: https://myrealdomain.com/
listen_addr: 0.0.0.0:80
tls_letsencrypt_hostname: "myrealdomain.com"

Note the attempt to use letsencrypt on the 3rd line. That causes the error

What will work (I have a working domain name in DNS):

server_url: https://myrealdomain.com/
listen_addr: 0.0.0.0:443
tls_letsencrypt_hostname: "myrealdomain.com"

Nathanaël: "When you set tls_letsencrypt_hostname, it will start an webserver on port 80 to serve the ACME validation file
That's why it doesn't work on your case, because you can't bind headscale + letsencrypt validation on same port (and let's encrypt require port 80)"

The stock config.yaml could have been more helpful, by stating something like this, near "listen_addr":

#If you don't plan to use headscale behind a reverse proxy - which would handle SSL itself - then you'll probably want SSL from LetsEncrypt, which headscale can obtain for you. So in that case use "listen_addr: 0.0.0.0:443" in production, in conjunction with stating your working DNS hostname that you'll use below, see "tls_letsencrypt_hostname"

In summary, the sensitivities of listen_addr and tls_letsencrypt_hostname (how they do or don't get along with each other) could be better explained in config.yaml

Also: The error message didn't mention the collision between headscale's use of port 80, and LetsEncrypt's use of port 80.
