### Current Behavior

After upgrading 0.26.1 → 0.27.1 → 0.28.0 → 0.29.4 (one step at a time), our two HA subnet routers never received a netmap again. We had to roll back to 0.26.1 by restoring the database. The policy uses **no `via` grant, no `grants` at all, and no `autogroup:self`** — only `groups`, `hosts`, `tagOwners` and `acls`.

**Tailnet size**

- 1026 nodes (100–180 online), 685 users, PostgreSQL
- 2 HA subnet routers advertising ~60 routes each. They have **946 peers each**; the average node has 5.9 peers (`/debug/nodestore`)
- Policy: 50 `acls` rules, 341 destinations in total, 54 groups listing 2056 usernames

**Symptoms on 0.29.4**

- headscale CPU: 4–9 cores (0.2–0.6 on 0.26.1, ~1.3 on 0.27.1 and 0.28.0)
- Almost every `/machine/map` request ends with `bytes=0`
- Routers register fine (`machineAuthorized=true`), then never reach `Running`
- Clients log `PollNetMap: ... unexpected EOF` every 60 s (reverse proxy read timeout). With the proxy timeout raised to 3600 s, they log `control: map response long-poll timed out!` every 120 s instead, and the request is queued again
- CLI calls exceed the 5 s deadline (`DeadlineExceeded`); `headscale nodes rename` took ~15 s

**Reproduced in isolation**: a local headscale 0.29.4 on a copy of the database, no reverse proxy, **a single client** registered as the router's user. One core is busy at 100 %, one map was eventually delivered after **96 s** (`bytes=366760 elapsed=96213`), the next request ended with `bytes=0` after 157 s because the client gave up at 120 s.

**On 0.26.1, same data, same router**: the netmap arrives within 1 second of registration, and a 30 s CPU profile shows 1.5 s of CPU in total.

**CPU profile on 0.29.4 (production, 6 s, 26 s of samples)** — 89 % of the time is in:

```
mapper.(*Batcher).worker
 mapper.generateMapResponse
  mapper.(*MapResponseBuilder).buildTailPeers
   types.NodeView.TailNode
    state.(*State).RoutesForPeer
     policy/v2.(*PolicyManager).ViaRoutesForPeer     23.27s  89.36%
      policy/v2.(*Group).Resolve                     23.11s  88.75%
       policy/v2.(*Username).resolve                 21.75s  83.53%
        policy/v2.(*Username).resolveUser            14.40s  55.30%
```

**Goroutine dump at the same time**: 106 goroutines waiting in `mapper.(*Batcher).MapResponseFromChange` (called from `AddNode`), 4 workers computing inside `ViaRoutesForPeer`, 2–3 workers waiting on a mutex in `Batcher.worker`.

**What we think happens (reading v0.29.4)**

Three factors multiply:

1. `buildTailPeers` (`hscontrol/mapper/builder.go`) calls `State.RoutesForPeer` → `ViaRoutesForPeer` for **every peer**, including peers that advertise no route at all (only 3 of our 1026 nodes have routes).
2. `ViaRoutesForPeer` (`hscontrol/policy/v2/policy.go`) converts every ACL to grants and resolves the sources and destinations of **all** of them before checking `len(grant.Via) == 0`. With no `via` grant in the policy, the result is always empty, so all that work is discarded. The function comment already says: "Hot callers should memoise by (policy-hash, viewer-id) rather than invoking this per-pair."
3. `aclToGrants` (`hscontrol/policy/v2/types.go`) emits **one grant per destination**, each carrying the full source list. Our 50 ACL rules become 341 grants, so a rule with 67 destinations has its sources resolved 67 times.

Each `Username.resolve` walks all users and then all nodes, with no cache, and a username matching no user also builds a formatted error.

For our policy this gives 17 691 username resolutions per (viewer, peer) pair, i.e. about 30 million comparisons per pair and about 28.6 billion for one map with 946 peers, which matches the ~96 s we measured.

Related: #3346 (same symptoms after 0.28 → 0.29.1, on a ~200 device tailnet).


### Expected Behavior

Netmap generation time on 0.29 should stay in the same order of magnitude as on 0.26 for a policy that does not use `via`.

Possible fixes, from cheapest to most complete:

1. In `ViaRoutesForPeer`, return early when no grant in the policy has a `via` tag (ACL-derived grants never have one). This alone removes the cost for every policy without `via`.
2. In `RoutesForPeer` / `buildTailPeers`, skip the via computation for peers that advertise no subnet or exit route.
3. Resolve grant sources and destinations once per policy change (or memoise per policy hash and viewer), instead of once per (viewer, peer) pair.
4. When converting ACLs with `aclToGrants` for this purpose, keep one grant per rule instead of one per destination.

We are happy to test a patch on a copy of our database.


### Steps To Reproduce

1. Use a tailnet with about 1000 nodes and several hundred users, and a policy made of `acls` rules only, with large groups as sources and many destinations per rule (ours: 50 rules, 341 destinations, 54 groups, 2056 usernames). No `grants`, no `via`.
2. Make sure at least one node can see most of the tailnet as peers (in our case a subnet router reachable by everyone: 946 peers).
3. Run headscale 0.29.4 and connect that node.
4. Watch `/machine/map` for that node: the first map takes about 96 s on an otherwise idle server with a single client, and is never delivered when other clients are connected. CPU stays at one full core per busy worker.

Workaround we are evaluating (computed, not yet fully measured): rewriting the `acls` rules as native `grants` with all destinations in one grant (`"ip": ["*"]`) brings the number of source resolutions per pair from 341 down to 52, and removing usernames that match no user brings username resolutions from 17 691 down to 1 025. The compiled filter (`/debug/filter`) is byte-for-byte identical to the one produced by the original `acls` policy.

Follow-up with measurements. We reproduced the problem offline on a copy of the database and measured each step of the upgrade path with a real client.

**Protocol**: database restored from a dump taken on 0.26.1, one Tailscale 1.102.5 client registered under the subnet router's user, its 60 routes advertised and approved, then the client restarted with its state. The timer stops when the client is `Running` and has received its peers. Same machine for all runs, no reverse proxy, no other client.

**First netmap for a node with 946 peers**

| Version | First netmap | headscale CPU time | Registering a node |
|---|---|---|---|
| 0.26.1 | 2.6 s | 0.1 s | 2.4 s |
| 0.27.1 | 10.3–11.3 s | 10–12 s | 20.0 s |
| 0.28.0 | 10.3–15.4 s | 11–16 s | 18.8–24.1 s |
| 0.29.4 | 82.8–86.1 s | 90–92 s | 11.9 s |

On 0.29.4, after a second restart of the client, the netmap was **never delivered within 600 s** (2 runs out of 2), with `map response long-poll timed out!` every 120 s.

**This is not a deadlock or an endless loop.** Goroutine dumps taken every 25 s during the failing case show one worker computing in `resolveUser` / `AppendToIPSet`, and `headscale_mapresponse_generated_total` keeps increasing slowly. The computation is simply too slow, and the work started for a request that the client has already given up on (after 120 s) is not cancelled, so the queue for that node never drains.

**Where the time goes** (CPU profiles)

| Case | Hot path | Share |
|---|---|---|
| 0.29.4, netmap of the router | `generateMapResponse → buildTailPeers → TailNode → RoutesForPeer → ViaRoutesForPeer → Group.Resolve → Username.resolve → resolveUser` | 90 % |
| 0.29.4, registering a node | `snapshotFromNodes → BuildPeerMap` | 59 % |
| 0.28.0, netmap of the router | `snapshotFromNodes → BuildPeerMap` | 77 % |

**Control experiment**: with an allow-all policy on 0.29.4, the same node gets its netmap in 2.8–7.2 s with 1026 peers. The cost comes from resolving the policy, not from the size of the netmap.

**Workarounds measured on 0.29.4** (no code change)

| Change | First netmap | After restart | Peers |
|---|---|---|---|
| none | 86.1 s | fails at 600 s | 946 |
| `tuning` (`node_store_batch_size=1000`, `node_store_batch_timeout=5000ms`, `batch_change_delay=10s`, `batcher_workers=4`) and `node.routes.ha.probe_interval: 0s` | 98.3 s | fails at 600 s | 946 |
| router converted to a tagged node | 88.8 s | not measured | 946 |
| usernames matching no user removed from groups | 43.9 s | 60.9 s | 946 |
| 477 stale nodes deleted (expired, or offline for more than 90 days) | 36.0 s | 44.8 s | 514 |
| `acls` rewritten as native `grants`, one grant per rule (52 instead of 341) | 19.4 s | 14.2 s | 946 |
| `grants` and unmatched usernames removed | 12.7 s | 12.6 s | 946 |
| `grants`, unmatched usernames removed, stale nodes deleted | 9.0 s | 4.6 s, 8.7 s | 514 |

With the last combination and 12 clients restarted together with headscale (2 routers, 10 regular clients): regular clients get their netmap in 7.9–9.4 s, routers in 12.6 s and 12.9 s.

The `grants` rewrite is equivalent: the compiled filter from `/debug/filter` is identical to the one produced by the original `acls` policy, and the router keeps its 946 peers. All variants pass `headscale policy check` on 0.29.4.

**Takeaways**

- Offline, stale and expired nodes still count as peers, so they cost as much as online ones.
- Writing the same rules as `acls` costs about 4 times more than writing them as `grants`, because `aclToGrants` emits one grant per destination and the sources are resolved again for each of them.
- An early return in `ViaRoutesForPeer` when the policy has no `via` grant should bring 0.29 back to the 0.28 numbers for policies like ours.

Correction to the description above: the 96 s figure came from a log line read during an earlier run; with the protocol described here the first netmap takes 82.8–86.1 s.

Possibly related: #3417, #3108, #3501, #3156.

We can run more measurements on this copy of the database, or test a patch, if that is useful.
