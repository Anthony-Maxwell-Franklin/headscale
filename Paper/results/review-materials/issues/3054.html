### Current Behavior

Add a user via the headscale API, e.g. "test@auth.kanidm.tld" (gets ID:1), no name or email.
Add the user to ACLs.
When user connects via OIDC provider a second user "test@auth.kanidm.tld" (gets ID:2) is added with the provided name and email.
The ACLs are checked against ID:1 and not against ID:2.
For ID:2 to work the ACL has to use the email for ID:2 to be matched.

### Expected Behavior

When a login via OIDC occurs, the API should check for the existence of the "preferred_username" and update the name and email of the previously registered user.

At the least there should be a unique index on Username to prevent the same Username being used twice.

### Steps To Reproduce

See Current Behavior

### Environment

```markdown
- Headscale version: Container 0.27.1
- Tailscale version: Arch Linux 1.94.1-1
```

### Runtime environment

- [x] Headscale is behind a (reverse) proxy
- [x] Headscale runs in a container

### Debug information

Until the ACL matches the email, the message `Drop: TCP{100.64.0.11:53278 > 192.168.1.3:443} 64 no rules matched` repeatedly appears in tailscaled log.

In Kanidm, you can [configure to use the username (instead of the SPN) as preferred_username attribute](https://kanidm.github.io/kanidm/stable/integrations/oauth2.html#short-names):

```console
kanidm system oauth2 prefer-short-username <client name>
```

Upon next authentication (or with `tailscale up --login-server https://headscale.example.com  --force-reauth`) the username gets updated to `user5` and the updated policy works just fine:

```json
{
  "acls": [
    {
      "action": "accept",
      "src": ["user5@"],
      "dst": ["100.64.0.1:*"]
    }
  ]
}
```

Created: 2026-02-10T07:52:58Z; updated: 2026-02-10T07:52:58Z

You may also use the `provider_identifier` to reference a user in the policy. [It prioritizes matching the `provider_identifier`, and if not found, it falls back to matching the Email or Name.](https://github.com/juanfont/headscale/blob/e0d8c3c877df8ac493dccc8cd280b688293d79b5/hscontrol/policy/v2/types.go#L233) The `provider_identifier` is not exposed in the CLI, but you can obtain it from the database (or probably API):


```sql
SELECT name, provider_identifier FROM users
```

Be sure to append `@` at the end, so the policy looks like this:

```json
{
  "acls": [
    {
      "action": "accept",
      "src": ["https://kanidm.internal/oauth2/openid/headscale/59ac9125-c31b-46c5-814e-06242908cf57@"],
      "dst": ["100.64.0.1:*"]
    }
  ]
}
```

This is especially useful for Kanidm where they allow users (with the appropriate permissions) to update all of their
attributes: name, username, email, …. See also the section ["Reference a user in the policy"](https://headscale.net/stable/ref/oidc/#reference-a-user-in-the-policy) in our docs.

Created: 2026-02-18T07:45:41Z; updated: 2026-02-18T07:45:41Z

> All the documentation says is Kanidm is fully supported by Headscale. then warns about the groups being fully qualified.

Its no warning, but just a hint that Kanidm sends group names as fully qualified. We've had some complaints in the past where authorization failed because users specified the group name as `mygroup` instead of `mygroup@kanidm.example.com`.

> So I don't understand your comment "recommend to use short names as Headscale username", would that mean that Username would then be unique as I thought they were?

No, its does not fix the uniqueness problem; its just a way to make it a bit less confusing. With short username enabled, the username looks like a regular username and not like an email address.

> I often see "run this SQL" but I have no idea where and how to do that, I run Headscale in a container, is there an API to call/execute SQL on a live instance?

Agreed, it isn't exposed by the CLI yet. We consider to expose arbitrary fields with the upcoming CLI rework. Currently scheduled for v0.30.0.

Yes, the provider ID can be retrieved from the API via the `/api/v1/user` endpoint ([docs](https://headscale.net/development/ref/api/#__tabbed_1_1)): `curl -H "Authorization: Bearer <API_KEY>" https://headscale.example.com/api/v1/user`

> The issue remains that I can't use anything legible in the ACLs because `https://kanidm.internal/oauth2/openid/headscale/59ac9125-c31b-46c5-814e-06242908cf57@` means nothing when going through the ACLs.

Yes, and its precisely the reason we don't mention it in the docs/changelog etc more prominently. For users that want to use the provider identifier there's the `groups` section in the policy that can be used as an alias. Minimal example:

```json
{
  "groups": {
    "group:alice": [
      "https://kanidm.internal/oauth2/openid/headscale/59ac9125-c31b-46c5-814e-06242908cf57@"
    ]
  },
  "acls": [
    {
      "action": "accept",
      "src": ["group:alice"],
      "dst": ["100.64.0.1:*"]
    }
  ]
}
```

A workaround and far from perfect, but at least more readable.
